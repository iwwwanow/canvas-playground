# ffmpeg / видео-анимация интеграция в xtc-toaster

Приоритет — npm-пакет / Node-сторона, не браузер (браузер под вопросом на потом, докер пока не рассматриваем). Для serverside-обработки видео ffmpeg не вендорится в код: берём `ffmpeg-static`/`@ffmpeg-installer/ffmpeg` (npm-пакет качает статический бинарник под платформу в postinstall) + `fluent-ffmpeg` как обёртку над CLI-аргументами, спавн через `child_process`. Актуальность ffmpeg поддерживается не руками, а простым бампом версии `ffmpeg-static` в package.json — обычная задача для Renovate/Dependabot.

Ключевая находка для интеграции с текущим пайплайном (`Layer`/composer работают в терминах `Uint8ClampedArray` RGBA): вместо PNG-секвенций гонять сырые кадры напрямую через pipe — `ffmpeg -i input -f rawvideo -pix_fmt rgba pipe:1`. Формат `rawvideo` без заголовков и разделителей — это плоский дамп байт, кадр за кадром, размер кадра = `width*height*4`. Поэтому width/height нужно знать заранее (через `ffprobe`), иначе не на что резать поток. Побайтовое совпадение с `ImageData.data` убирает энкод/декод PNG из цикла и даёт кадр в готовом для существующего пайплайна виде.

Видео при этом не грузится целиком в память — `ffmpeg.stdout` читается чанками, кадр собирается по мере накопления `frameSize` байт и сразу уходит дальше в обработку; пиковая память — один кадр плюс небольшой хвост. Если downstream-обработка кадра асинхронная/медленная, нужен backpressure (pause/resume стрима или `Transform`), иначе копится необработанный буфер на стороне Node.

Этот же pipe-паттерн (`ffmpeg stdout → куда-то`) естественно продолжается в сторону будущей цели «считать на сервере, стримить на клиент»: фрагментированный MP4 (`-movflags frag_keyframe+empty_moov`) или HLS-сегменты пишутся ffmpeg в тот же stdout, который просто перенаправляется в HTTP response — но это отдельная задача на потом.

Порядок работ: сначала довести image-processing функционал либы, только затем браться за видео/анимацию.
