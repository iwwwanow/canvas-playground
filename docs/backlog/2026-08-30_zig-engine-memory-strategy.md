# Стратегия памяти для Zig-движка — вдохновение от libvips, arena allocator

libvips — не просто набор операций (по охвату сравним с OpenCV: resize/convolution/морфология/ICC), а именно способ их исполнения: граф операций, вычисляемый лениво по регионам/тайлам, а не аллоцируя буфер на всё изображение сразу — так гигапиксельные изображения обрабатываются без раздувания памяти. Сам набор операций тянуть в проект не стоит (конкурирует с тем, что сознательно строится руками на Zig), но паттерн исполнения стоит позаимствовать концептуально для собственного Zig-движка — особенно учитывая, что это первый в проекте заход на ручное управление памятью.

Практический стартовый паттерн — **arena allocator**: на каждую операцию (один composer/effect над одним буфером) выделять из арены, в конце операции освобождать всю арену разом одним вызовом, вместо ручного парного alloc/free на каждый промежуточный буфер. Хорошо ложится на форму существующих doman-функций («взяли входной буфер → посчитали → отдали выходной буфер»). Тайловая/региональная обработка (аналог libvips) — естественное развитие этого же паттерна на будущее, когда буферы станут большими (видео-кадры, гигапиксельные изображения) и понадобится не aллоцировать всё сразу.

Отдельно: главный источник багов с памятью в этой связке — не сама Zig-математика, а **FFI-граница** (JS↔Zig): кто владеет буфером и кто его освобождает нужно зафиксировать явно и последовательно, иначе — use-after-free/double-free/утечки. Стоит быть особенно внимательным здесь при обкатке первого FFI-паттерна.

Лестница сложности для ручного освоения (совпадает с планом «сначала одна простая функция + FFI руками, обкатать паттерн, затем агент — остальной 1:1 порт»): composers/blend modes (фиксированный размер входа/выхода, простой alloc/free) → convolution/blur (нужен паддинг на границах, возможно scratch-буфер под ядро) → transforms с интерполяцией (сложнее геометрия, but та же память).
