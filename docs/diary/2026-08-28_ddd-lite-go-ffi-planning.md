# 2026-08-28 — DDD-lite для core-либы + план переноса domain на Go/Zig

Начали с вопроса «насколько уместен DDD» для `legacy/packages/core/lib` (composition → layer → pixel пайплайн). Пришли к выводу: не полноценный DDD (нет персистентности и инвариантов, ради которых нужны repositories/domain events/bounded contexts), а просто domain/application/infrastructure слоение + инкапсуляция через aggregate root — `Composition` (root) создаёт и отдаёт `Layer` (child entity), domain-services (cutters/composers/reducers) — чистые функции ниже сущностей, вызываются только изнутри entity-методов, use-case (тосты) их не видит и не создаёт `Layer` напрямую.

Дальше разговор ушёл в отдельный, более крупный план: перенести саму domain-часть (pixel-math) на Go, вызывать из Bun через FFI. Разобрали handle-паттерн для передачи Go-объектов через C ABI, zero-copy через `runtime.Pinner` (обоснован именно под видео/батч-нагрузку, для разовой картинки был бы overkill), dev-loop одним `watchexec`-процессом вместо связки air+bun-watch (полный рестарт процесса обязателен — cgo shared lib нельзя перезагрузить в живом процессе), и стратегию защиты от рассинхрона ручных биндингов с Go-экспортами через contract-test вместо AST-кодогена.

Полные технические детали и обоснования решений — `docs/backlog/2026-08-28_ddd-lite-go-ffi-architecture.md` (по факту один план, не два: домен целиком переезжает в Go/Zig, TS-биндинги (`bindings/*.binding.ts`) — чистый адаптер/порт без собственной бизнес-логики, зеркалящий сущности 1:1).

**Под конец сессии выбор языка пересмотрен в пользу Zig.** Разобрали реальный domain-код (`cutters/*`, `Layer.addHueNoize`) — везде один паттерн: цикл по `Uint8ClampedArray` с арифметикой, без сложных структур. Zig-специфичные сложности (comptime-generics, кастомные аллокаторы) тут не нужны — хватает примитивных `[]u8`-слайсов, то есть исходное опасение "Zig слишком низкоуровневый" не подтвердилось при взгляде на реальный объём работы. Ключевой плюс: у Zig нет GC — вся конструкция с `runtime.Pinner`/handle-registry-ради-GC-безопасности и открытый риск "GC-пауза Go сорвёт видео-кадр" у Zig просто не существует как класс проблем. Контраргумент, который нашли: Bun сам в мае 2026 переписался с Zig на Rust — не из-за FFI (`bun:ffi` одинаково дёргает `.so` вне зависимости от языка сборки), а потому что Zig всё ещё pre-1.0 (0.16, ломающие изменения между релизами) — для личного проекта не блокер, но версию нужно будет пинить осознанно. **Финальный выбор Go/Zig не закреплён** — предстоит решить на шаге «начертить domain».

Решено: тосты остаются в TS (application/use-case layer), но их нужно переписать под новую сигнатуру — сейчас `bake(data: Uint8ClampedArray, ...)`, после переезда домена в Go будет `bake(layer: Layer, ...)`, где `Layer` — TS-обёртка над Go-сущностью.

## Открытые вопросы

- ~~Go или Zig для domain-части~~ — **закрыто 2026-08-29: Zig.**
- ~~Тосты остаются в TS или тоже переезжают~~ — **закрыто: остаются в TS**, но переписываются под новую сигнатуру `bake(layer: Layer, ...)` (см. выше).
- ~~mosaic-segment — bounded context или вне скоупа~~ — **закрыто 2026-08-29: вне скоупа, следующей итерацией.** Не зависит от Layer/Composition (работает напрямую с `Uint8ClampedArray` → `Segment[]`), поэтому перенос домена его не блокирует.
- ~~y-rotation-perspective — заходит в transforms или особняком~~ — **закрыто 2026-08-29: заходит в семейство transforms**, наравне с affine (translate/rotate/scale/skew), отдельной веткой (не через 3×3-матрицу — perspective divide, а не аффинное преобразование).
- Реальный техдолг, не зависящий от переезда на Go/Zig: `Composition` сейчас мешает DOM/canvas-код (infrastructure) с доменной логикой (`layers[]`, render pipeline) — стоит вынести в отдельный `CanvasRenderer`, оставить `Composition` без `document`/`HTMLCanvasElement`. Всё ещё открыто.
